# Yappa

A personal Twitch chat client (tabs, video, 7TV/BTTV/FFZ, mod tools, chat-color cycling) running
as a Cloudflare Worker at https://yappa.0x9.ca, open only to allowlisted Twitch accounts (Twitch sign-in, no Cloudflare Access). Installable as a PWA.
A previous hostname can keep routing to the Worker (an extra entry under `routes` in `wrangler.jsonc`).
Its page (`src/moved.ts`) forwards to `APP_HOST`, carrying the browser's localStorage in the URL
fragment; `app.js` imports it into a fresh browser. API routes still answer there, so copies of the
app that are already open keep working.
The deployed Worker keeps the `name` it was first created with (set in the gitignored `wrangler.jsonc`; the project started life as a chat-color prank). Its Durable Object data is tied to that name, so never change it.

## Commands

- `npm run check`: type-check the Worker (`tsc --noEmit`). Client JS isn't type-checked; run `node --check src/client/app.js`.
- `npm test`: both test suites (see Testing); run it before every deploy. `npm run test:unit` is the fast, browser-free half (about a second); `npm run test:e2e` the browser half (about a minute).
- `npm run deploy`: `wrangler deploy` to the custom domain. Deploying is how changes reach the user; there is no staging.
- `npm run types`: regenerate `worker-configuration.d.ts` after changing `wrangler.jsonc` bindings or vars. That file is gitignored (it embeds the config values), so run it after cloning too; `npm run check` needs it.

## Architecture

- `src/index.ts`: Worker entry. Public: the app's static files, the old-hostname redirect, and `/auth/login` + `/auth/callback`. Everything else needs a session: `GET /` without one is the sign-in page (`renderLogin`), the API answers `401 {signedOut:true}`. The callback exchanges the code *in the Worker*, validates the token, checks the allowlist (`isAllowed`), revokes the grant and keeps nothing for strangers, else hands the tokens to that account's Durable Object (`storeTokens`) and sets the cookie. The allowlist is re-checked on every request. Error codes (`?error=denied|state|failed|cancelled`) are fixed strings, never reflected text. POSTs require a same-origin `Origin` header (CSRF).
- `src/session.ts`: the sign-in cookie (`__Host-yappa_session`: Twitch id, login, expiry; HMAC-signed with the `SESSION_SECRET` secret; 30 days, renewed on page loads) and `isAllowed` (`ALLOWED_LOGINS`: logins and/or numeric ids; empty = nobody).
- `src/tools.ts`: request checking, plain-words failures and trimmed shapes for the moderator tools, whispers, block list, subscription check and discovery (`TOOL_SCOPES` lives here; `OPTIONAL_SCOPES` includes them). `src/client/tools.js` is the matching client half: a second classic script loaded after app.js, wrapped in an IIFE (so its names can't clash with app.js's globals), reaching app.js's globals directly and called back through `window.tools*` hooks (`toolsHandleEvent`, `toolsRenderInfo`, `toolsUserCardActions`, `toolsAccountItems`, `toolsOnSession`, `toolsFollowExtra`).
- `src/color-loop.ts`: Durable Object class `ColorLoop` (historical name), one per Twitch account, named by Twitch user id (it used to be one per Cloudflare Access email, so tokens stored then were orphaned; signing in again recreates them). It owns the Twitch tokens (refresh, hourly validation), the color-cycling state, and every Helix call, exposed as RPC methods. **Don't rename the class, the `COLOR_LOOP` binding or the Worker**; that orphans the stored tokens and settings.
- `src/app-token.ts`: public Twitch lookups (live status, clips, badges, cheermotes) answered in the Worker with a shared app access token, so polling doesn't wake Durable Objects. Anything needing the user's identity or permissions belongs in the Durable Object.
- `src/twitch.ts`: OAuth and Helix helpers. `SCOPES` are required. `OPTIONAL_SCOPES` power the emote list and mod tools; adding one means the user must reconnect (the client shows a banner from `missingOptionalScopes`).
- `src/page.ts`: the HTML shell. `src/static.ts`: client assets, icons and the web manifest, served with content-hash `?v=` URLs. `APP_NAME` lives here.
- `src/client/{app.js,app.css,sw.js}`: plain browser JS/CSS with no build step and no TypeScript, imported into the Worker as text modules (`rules` in `wrangler.jsonc`; declarations in `src/client/modules.d.ts`). Keep client code here, not in TS template strings: escapes like `\s` silently break inside template literals.
- `scripts/draw-social.mjs [out.png]`: renders `scripts/social-preview.html` to the GitHub social preview (1280×640, default `docs/social-preview.png`; upload it under the repo's Settings → Social preview by hand, GitHub has no API for it). `SHOTS_FONTS` makes it render in Roboto like the screenshots.
- `scripts/draw-icon.mjs <outdir>`: draws the app icon (a rainbow chat bubble with a `#`) on a headless Chromium canvas and writes all icon sizes plus a 1024px preview to `<outdir>`. Copy the five icon PNGs into `src/client/icons/`; the preview isn't used.

The browser talks to these directly:
- **Twitch EventSub WebSocket:** one shared socket for all tabs. The Worker creates the subscriptions against the socket's session id.
- **Anonymous read-only Twitch IRC:** only for `first-msg` flags, which EventSub lacks.
- **recent-messages.robotty.de:** history and reconnect backfill, **only after the user opts in** (`settings.history`: `null` = not asked yet). The service's guidelines require consent, a short explanation and a link to it, both in the opt-in prompt and in Settings. Keep that if you touch it. History comes in pages of 100 (`HISTORY_PAGE`, within the service's recommended 50–100): the newest page on first load, older pages via `before=` as you scroll up (`loadOlder`), and reconnect gaps via `after=`. Lists are trimmed only while you're at the bottom.
- **7TV / BTTV / FFZ APIs.**
- **The Twitch embed player** (`player.twitch.tv/js/embed/v1.js`).
- **Native player (opt-in, Settings → Video player):** the browser asks Twitch's internal GraphQL API (`gql.twitch.tv`, using the Client-Id of Twitch's own website) for a playback token, then plays the `usher.ttvnw.net` HLS playlist in a `<video>`. Twitch's usher only sends CORS headers for twitch.tv origins, so hls.js (XHR) can never read the playlist from our origin; it stays only as a last resort (light build, served as `/hls.js`, `enableWorker: false` because the CSP forbids blob: workers). What works is a plain `<video src>` using the browser's built-in HLS: tested working in Firefox for Android, failing in Chrome for Android (source not supported). The Twitch embed has the opposite result (works in Chrome; in Firefox for Android its script fails to load, likely tracking protection or an ad blocker), so the setting is per browser and users pick whichever works. When the embed script can't load, `showEmbedBlocked` explains it in the video box with Try again / Use native player; it never retries on its own. Making it work in Chrome would mean proxying video through the Worker, which was deliberately not done (Twitch's terms, request volume, the IP-bound token). This is unofficial and can break at any time. Any failure falls back to the embed for the session (`nativeFail`). Once playing, a stall (`nativeWatchdog`: playing but no progress for 10s), the stream "ending", or a media error reconnects with a fresh token (`nativeRestart`, saying so in chat with the video's recent events, since the cause of the stops was unknown); after 3 restarts in 2 minutes it gives up and uses the embed. The token request and all video stay in the browser. **Quality selection**: a built-in-HLS `<video>` can't be told which rendition to use, so the page plays a rendition's own playlist URL; that needs the master playlist, which usher won't serve to our origin (CORS), so `POST /api/hls/master` (`src/usher.ts`) relays that one small text file (strict input checks, usher host only, audio-only allowed so it can be listed). Never proxy variant playlists or segments through the Worker. The Auto URL deliberately omits `allow_audio_only` so an adaptive player can't pick it. The saved choice is `settings.nativeQuality` (a GROUP-ID like `720p60`, `chunked` = source, `audio_only`, or `auto`) and is re-applied on every (re)start via `pickVariant`. Whether usher answers a Worker's request as it does a browser's is unverified: failures just mean no quality button.

Tokens never reach the browser.

## Gotchas (learned the hard way)

- **The Durable Object can keep running old code after a deploy.** The Worker calls `syncVersion()` on every page load and once per isolate per user otherwise, and the DO `ctx.abort()`s itself if the Worker is newer. The Worker also maps "does not implement the method" RPC errors to a `503 {retry: true}`, which the client retries. After deploys that change `color-loop.ts`, confirm the switch-over: query Workers Observability for `jsrpc`/`alarm` events and compare `$workers.scriptVersion.id` with the deployed version. `console.log` JSON lands in the event's `source` field.
- **Stay compatible with data written by older versions:** DO storage and client `localStorage` (`settings` migrations in `loadSettings`). Use `structuredClone(DEFAULT_SETTINGS)` so the defaults' arrays aren't shared.
- **Failures must never look like empty answers.** The public lookups (`/api/streams`, badges, cheermotes) answer `502 {ok:false}` when Twitch can't be reached, and the client keeps its previous state: an empty list would mark every channel offline and pause the video. When the sign-in cookie expires (or the account leaves the allowlist) the API answers `401 {signedOut:true}`; `api()` shows the "Sign in again" banner.
- **The page has a Content-Security-Policy** (`PAGE_HEADERS` in `src/page.ts`): scripts only from our origin and `player.twitch.tv`, no inline scripts or `on*=` attributes, and no framing. Loading a script from a new host means adding it there. Images, fetches and sockets aren't restricted.
- **Token refreshes are single-flight** (`ColorLoop.refresh`). Twitch can rotate the refresh token, so two concurrent refreshes could spend it twice and log the user out.
- **Message lists are kept in time order.** Every `<li>` has `data-ts` (set in `append`, or from the event). History merges in with `insertByTime`, so don't insert list items any other way.
- **The message box is `contenteditable`** (so finished emote names render as images). Emotes in it are text spans with the image as their background, never `<img>`: phone keyboards predict from the text before the caret. `render()` only rebuilds nodes that changed. Typing a whole emote name adds the trailing space itself (`autoFinishEmote`; skipped when a longer emote starts the same way, for all-lowercase names, and for deletes/pastes; a habitual space typed right after is swallowed by the `beforeinput` handler). Always go through the `composer` API (`getText`, `setText(text, caret)`, `caret`, `focus`, `setEnabled`); never `.value`.
- **Two themes.** Colors are CSS variables on `:root` (dark), overridden by `:root[data-theme="light"]`. Use a variable for any new color, unless it sits on the video (always dark) or is white text on the accent color. `src/client/theme.js` sets `data-theme` in `<head>` before first paint; `applyTheme` in app.js keeps it current. Chat names go through `paintName`, which darkens bright names on the light theme.
- **Emote tooltip** (`showEmoteTip`, `placeEmoteTip`): every emote image in chat carries `data-emote`/`data-source`/`data-detail` (set by `emoteImg`); tapping one in a message body shows a popover instead of selecting the message. Twitch emote ownership comes from the EventSub fragment's `owner_id` (history lines lack it, so `twitchEmoteDetail` falls back to the account's emote list groups). The tip follows its emote as chat auto-scrolls and closes when it leaves view.
- **Badge explanations** (`badgeMeaning`): the user card lists the badges on the clicked message. Twitch's badge description is usually just its title, so the common sets (broadcaster, moderator, vip, subscriber tiers/months, bits, gifts, ...) are explained by us; anything else falls back to Twitch's description, then its title, then the raw set id. Only add a set once you're sure what it means.
- **Moderator/personal tools** (all `/api/mod/*`, `/api/sub`, `/api/blocks`, `/api/whisper`, `/api/discover/*`, `/api/schedule`): every call checks the scope first (403 `needsScope` → the panel shows a reconnect link) and Twitch decides whether this account may moderate the channel (`moderator_id` is always the signed-in user). EventSub feeds are best-effort per channel: suspicious users (`channel.suspicious_user.message`, which arrives *besides* the normal chat message, so either can come first), unban requests, and, only if `settings.modLog`, `channel.moderate` v2. Whispers arrive via `user.whisper.message` (one subscription per socket, `/api/whispers/subscribe`) and are kept in memory only. Shared chat is detected from a message's `source_broadcaster_user_id` rather than the `channel.shared_chat.*` events, because EventSub WebSockets allow only a few subscriptions that need no authorization (max_total_cost 10). Go-live alerts poll the followed list every 2 minutes (no per-channel EventSub for the same cost reason). The block list (`blockedIds`, `settings.syncBlocks`) is merged into `isHidden`.
- **Info bar:** icon buttons sit 2px apart (`.infobar` gap), the bar wraps to a second row when crowded, and a stream title too long for its space slides back and forth (`fitTitle`, `.title.scrolls`, off under reduced motion). Chat modes live in the Mod tools sheet (`modesPanel` in tools.js; there is no separate Modes button or panel any more); the mode chips next to the title are just a read-out.
- **Pinned stream** (`pinnedLogin`, `videoTab()`, `setPinned`; saved in localStorage `pinnedVideo`): the video box shows `videoTab()`, the pinned channel's tab if it's live, else the open tab. Always use `videoTab()`, not `active`, for anything about the stream being shown. Closing the pinned tab unpins (logging out keeps the pin).
- **Sync** (`src/sync.ts`, `/api/sync`, `ColorLoop.getSync/putSync`, app.js "sync between devices"): one blob per account (settings minus `DEVICE_SETTINGS`, the saved tab list, the pinned stream), newest `at` wins, pushed 2s after a change (`syncChanged`, hooked into `saveSettings`/`saveTabs`/`setPinned`, skipped if the content equals `syncedJson`), pulled before `restoreTabs` (3s cap) and when the page becomes visible. Tabs and the pin are only adopted at startup. New per-device settings must be added to `DEVICE_SETTINGS`; anything else in `settings` syncs.
- **Links in pasted HTML**: `appendText` splits `<tag>`s off as text and `parseLink` leaves quotes, brackets, `attr="` and a trailing tag or quote outside the URL; live and history lines share this path.
- **Sending on a phone** keeps the keyboard up: `#send` cancels `mousedown` so the Chat button never takes focus from the message box (refocusing afterwards can not reopen a closed keyboard on iOS).
- **Chat search** (`applyFilter`): filters the open list in place; while it is open `trimList` pauses, and "Search earlier" (`#search-older`) loads one more history page via `loadOlder`.
- **Mute filters** (`settings.mute`, `isMuted`): hidden like ignored users (`.ignored` + `data-muted` so block-list reloads keep them hidden); never your own messages. **Mentions / All chats / stream stats / slow-mode note / export / extra shortcuts** live in tools.js (`toolsMention`, `toolsMirror`, `toolsSent`, `toolsActivated` hooks). All chats clones rendered lines (read-only), so it needs no per-message handlers. Slow-mode countdown is informational only (VIP exemptions can't be detected).
- **Emote picker groups**: `/api/chat/emotes` adds `owner` (display name via Get Users, remembered per Durable Object instance) to "Other channels" emotes; the picker makes one section per owner.
- **Personal settings** all live in `settings` (so they sync, unless listed in `DEVICE_SETTINGS`): `channels[login]` (`notify`/`sound`/`live` = on|off|absent, `muteWords`; read through `chanSetting`, edited with `setChan` in tools.js), `notes[userId]` (label, color, note; `userTag`/`refreshUserTags` render the label after names; capped at 300), `snippets`, `favEmotes`, `bookmarks`. Chat layout options (`compact`, `zebra`, `showTime`, `showBadges`, `chatFont`) are per device and become classes on `.app` in `applySettings`. Backup/restore (`backupFile`/`parseBackup`) accepts only keys that exist in `DEFAULT_SETTINGS` with the same type; add new settings there or they won't restore. Reload goes through `nav.reload` (test seam).
- **Tab menu and second stream** (tools.js): tab order is the `tabs` Map's order, changed only through `moveTab`. "Watch alongside" is a plain `player.twitch.tv` iframe in `#video2`, only at 1000px+ (the `dual` class adds a grid column); it is separate from the main player so `renderVideoNow` never touches it (`toolsVideoChanged` re-evaluates it). Never overlay it on the main player.
- **Startup order (keep it fast):** the first `/api/status?sync=1` carries the synced settings (`adoptSync`), then `restoreTabs`; on the socket's welcome `subscribeAll` joins the open tab first and the rest three at a time (a join is ~10 Twitch calls). A join waits only for badges, cheermotes and 7TV/BTTV/FFZ (`loadTabExtras`); the account's Twitch emotes are a long paged list, so `ensureTwitchEmotes` loads them for the open tab only (others on first activation) and the Durable Object keeps each channel's list for 5 minutes. A background tab's first page of history waits until it's first opened (`pendingHistory`; reconnect gaps still fill at once). The Durable Object also caches channel lookups, shares in-flight followed-channel and moderated-channel fetches, and `chatSubscribe` requests everything for a channel at once. The open channel's newest history is requested as soon as the script runs (`prefetchHistory`, from the URL hash or `lastChannel`), in parallel with sign-in and joining; the join then fills only the gap since (`backfill` with `since`). `GET /` doesn't touch the Durable Object; the first `/api/status?sync=1` of a page load is what forces the Durable Object onto the current deploy (`currentStub`). Settings → "Startup timings" shows where a real load spent its time (`startupMark`); look there before guessing. Never make chat or history wait on something slow again.
- **Settings** (`openSettings`) is a list of collapsible sections (`group(id, title, summary, items)`), one open at a time (remembered in `settingsGroup`), each holding `item(title, ...rows)`s; the search box shows the items whose text matches. Put a new setting in the right `group` as an `item` (give it a title and a hint so it can be found). In tests `openSettingsUI()` expands every section; pass `{ expand: false }` to test the sections themselves.
- **Link previews** (`src/previews.ts`, `GET /api/preview/x`, tools.js `toolsLinkPreviews`): an X/Twitter post link gets a card. X has no usable public API, so the Worker asks mbedfx (`mbedfx.app/_api/v1?url=https://x.com/i/status/<id>`, an unofficial, keyless public service with documented JSON, `docs/API.md` in its repo; it can change or disappear) and passes on a trimmed `XCard` (answers are remembered 15 min, failures 2 min, at most 3 requests at once because the service asks callers to space out distinct ones; a cold post can take several seconds, hence the 12 s timeout). Going through the Worker keeps the viewer's address from that service. mbedfx puts every avatar and picture behind its own `/_media/` URLs that redirect to X's CDN, so the Worker follows that one redirect itself (`resolveMedia`) and the browser loads pictures straight from X's CDN, never from mbedfx: only https `*.twimg.com` URLs are ever passed on (checked in the Worker and again in the client), they carry no referrer, and a post marked sensitive never loads its media. mbedfx's `text` is what its own card shows (it can carry its notes such as a translation marker or an age-restriction line) and it has no verified flag, so the card never shows one. **Imgur albums** (`src/imgur.ts`, `GET /api/preview/imgur`, `imgurCardEl`): with `images` on, `imgur.com/a/<id>` and `imgur.com/gallery/<slug-id>` links get a card (title, count, first four pictures, the first large (`<id>h.jpg`, 1024px) and the rest `<id>l.jpg` (640px), loaded by the browser). The Worker asks Imgur's API (`/3/album/<id>`, then `/3/image/<id>` for a single picture) with the client id of imgur.com's own web app: unofficial, it can break or be rate-limited; answers cached 15 min, failures 2 min; mature albums load no pictures. "Show a picture under messages that link to a .png, .jpg, .gif or .webp, and a small card with the first pictures for Imgur albums. Off by default: pictures load from whatever site the link points to, which can see your address." image links (`images`, off by default) load from arbitrary sites, so they're opt-in, and the probe image must not be `loading="lazy"` (a detached lazy image never loads).
- **Channel info and `/user`**: `GET /api/channel/info` (Get Channel Information + Get Users) and `GET /api/lookup/user?login=` answer with the app token like the other public lookups; the info sheet (`openChannelInfo`, opened from the info bar's live chip, which also works offline) shows what Twitch says about the channel and adds the live stats from `tab.stream` / `tab.viewerSamples`. `/user` goes through `runCommand` to `toolsLookupUser`, which opens the normal user card.
- **Diagnostics** (Settings → Diagnostics, `toolsDiagnostics` in tools.js, `GET /api/diag`): the Worker adds the deployed version, the Durable Object's `diag()` adds the granted scopes and token timing (never the tokens). `SCOPE_INFO` in tools.js lists every optional permission with what it's for; add new scopes there too. `api()` keeps the last 20 failures worth knowing about (`apiErrors`: network errors, 5xx, 401/403/429).
- **Moderator presets** (`settings.modPresets` = `{ timeouts: [seconds], messageTimeout, reasons }`, read only through `modPresets()` so a damaged saved value falls back to defaults; max 8 lengths, up to Twitch's 14 days): they drive the user card's timeout buttons, the message menu's Timeout and the reason picker (a picked reason is sent with the timeout or ban).
- **Quick switcher** (`openSwitcher` in tools.js; Ctrl/Cmd+K is caught in the capture phase so it wins over the browser and the composer): entries are built fresh each time by `switcherEntries()` (open tabs, followed channels once loaded, actions, one "Settings: <section>" per group in `SETTINGS_SECTIONS`, which must match the groups in `openSettings`) and ranked by `fuzzyScore`. Add new actions there.
- **Translation** (tools.js): manual (message menu) and per-channel automatic (`settings.channels[login].autoTranslate`, `autoTranslate`) both use the browser's own on-device `Translator`/`LanguageDetector` where they exist (recent Chrome; the test Chromium has real ones, so tests delete or fake them). The detector and translators are kept per API object, a failed creation is never remembered, and automatic translation runs one message at a time (max 20 waiting), skipping short, own and historical messages. Without the API the message menu opens Google Translate instead (only when tapped).
- **Accessibility** (keep it working; the e2e suite checks most of it): the tab bar is a `tablist` with `role=tab` buttons whose `aria-label` carries the whole state (`updateTabEl`); each chat list is a `role=log` with `aria-live` (off when `settings.announce` is false, a per-device choice); the sheet moves focus in, traps Tab (closed `<details>` contents are excluded by hand because they still report layout boxes) and returns focus; label+control rows tie the two with `aria-labelledby`; and a scan in the tests fails if any visible control (main screen, Settings, user card, Mod tools) has no accessible name. The third theme, `contrast`, is the `:root[data-theme="contrast"]` variables block (ratios are tested); "Match device" picks it from `prefers-contrast: more`. New screens should add their controls to that scan.
 With the video on, the layout puts it beside the chat (video left, chat column right) when the window is 1000px+ wide *or* a phone is on its side (`orientation: landscape`, height ≤ 520px, width ≥ 560px; the chat column shrinks to 280–380px); upright phones stack video over chat. The document never scrolls (only message lists do), and the app is sized to `visualViewport` via `--app-height`. Percent heights inside the footer resolve against the footer; use `--app-height`.
- **Twitch API limits:**
  - Hex chat colors need Turbo/Prime, and chat color is account-wide.
  - **Clips & VODs** (`src/browse.ts` holds the pure request checking, mapping and error wording). Browsing uses Get Clips / Get Videos with the app token (`app-token.ts`, no login needed; Get Clips is most-viewed first, a missing date range means all-time). Creating a clip (Create Clip, `clips:edit`, an *optional* scope so it needs a Reconnect) works only on a **live** channel, takes 5–60 s and a title (Yappa fills in the stream's title when you give none, `defaultClipTitle`), returns 202 with an id + `edit_url`, and the clip appears in Get Clips a few seconds later (Twitch: treat as failed after about a minute; `createClip` polls `/api/chat/clip`). Create Clip From VOD exists but only for a channel's editors, so it isn't offered. Playback uses Twitch's embeds with `parent=`. When `settings.postClips` is on, the clip's URL is sent to chat as the user via `sendChat` (the one place that sends a message and tracks its id for color cycling).
  - **"Your clips"**: Twitch's Get Clips can't filter by who *made* a clip (only channel, game or ids), so the Durable Object keeps its own list of the clip ids created through Yappa (`clips` storage key, tagged with the user id, newest first, capped at 500) and `/api/my/clips` turns a page of ids into details with Get Clips by id (deleted clips drop out). Clips made on Twitch itself can't be listed. The profile picture and display name come from Get Users, cached daily in the `profile` key and returned by `/api/status`.
  - **Clip cards in chat** (`attachClipCards`, `fetchClip`): lookups run at most 4 at a time, a failed lookup is retried (2 s, 6 s, 15 s), and "Twitch has no such clip" is remembered for only 60 s because a just-posted clip isn't in Get Clips for a few seconds. Remembering it forever left clips linked live without a card when the same message came back through history.
  - **Watch streaks, channel points and drops** are not earned by watching in Yappa's embed: a 30-minute test (embed, signed in, tracking protection off) didn't advance a streak, and a Twitch developer-forum thread says embedded players don't support community points. Twitch documents nothing either way. Don't claim otherwise, and never simulate watching (view-botting); the way to keep a streak is to watch on twitch.tv or the Twitch app (the gem button hands off there).
  - **Follow / unfollow**: Twitch removed its follow and unfollow API (2023), so Yappa can't do either. The heart button in the info bar (`renderFollowBtn`) shows the status from the followed-channels list (`/api/following`, `user:read:follows`) and opens the channel on Twitch to change it; coming back to the tab refetches with `?fresh=1`.
  - **GIFs** (Tier 2+ subs): EventSub `channel.chat.message` fragments of `type: "gif"` carry `gif.url` (the docs also name an id field, inconsistently `id`/`gif_id`, which we don't use); IRC/history carries a `gifs` tag, `start-end|id|url` entries positioned like `emotes` over bracketed placeholder text. Twitch requires the URL be used **unmodified**: never rewrite, proxy or resize it. Only `https` is loaded (`appendGif`); Settings → Show GIFs swaps the image for a link.
  - **Bits Power-ups.** Documented: `channel.chat.message` `message_type` values `power_ups_gigantified_emote` and `power_ups_message_effect` (undefined in the docs, no extra fields), and the `channel.bits.use` event (`power_up.type` message_effect / gigantify_an_emote / celebration, `message_effect_id`), which is broadcaster-only like the channel points events. *Not* documented: IRC tags and rendering. Seen in real raw IRC: `msg-id=gigantified-emote-message`, with the emote in the normal `emotes` tag. We enlarge the message's last emote (`renderFragments`, `giant` class; third-party sources and observed lines agree, Twitch doesn't say). Message effects can't be reproduced: the effect id and its visuals aren't available to viewers (no tag was found in ~2,000 sampled real messages). Spending Bits isn't possible through any API (hence the gem button).
  - Channel points redemption events (EventSub `channel.channel_points_*_redemption.add`) need the *broadcaster's* `channel:read:redemptions` grant, so a viewer can't subscribe in other channels. The only redemptions visible are those chat carries: `message_type` `channel_points_highlighted` / `channel_points_sub_only` and `channel_points_custom_reward_id` (IRC: `msg-id`, `custom-reward-id`), marked by `pointsLabel`. No reward name or cost is available.
  - Bits and channel points can't be used through the API, and Twitch's chat embed doesn't offer them (per Twitch staff; old forum threads), so the gem button next to the emote button hands off to Twitch itself (`openOnTwitch`): pop-out chat window on desktop, `twitch://stream/<channel>` on touch devices with a twitch.tv fallback. `launchers` is the test seam.   - The embed iframe doesn't allow picture-in-picture by default; the client patches `allow` when creating the player.
  - **Never draw anything over the player or replace its controls.** Twitch's embed terms require Twitch-approved player elements only, never obscured by other page elements, and the player refuses to play when covered. (Custom touch controls were tried and had to be removed.)
  - Twitch documents a 400×300 minimum for embeds, and autoplay needs a visible player of that size, but autoplay never works on mobile anyway (the user must tap play). The phone layout is a plain 16:9 box (about 220px tall) so there are no letterbox bars; playback works at that size. Padding the box to 300px was tried and removed for the bars it caused.

## Testing

`tests/unit.mjs` (no browser) checks the Worker's request validation, the usher relay and the Worker itself run directly in Node (sign-in, sessions, allowlist, sync) with the Durable Object faked; `tests/support.mjs` bundles the code for it. `tests/e2e.mjs` loads the real page and client JS in headless Chromium at phone size (390×760) and fakes everything external. That covers the `/api` routes (stateful mocks), the EventSub and IRC WebSockets, the recent-messages service, the 7TV/BTTV/FFZ CDNs, the Twitch embed script and Document Picture-in-Picture. It also runs the Worker itself in Node (Durable Object runtime faked) to test sign-in, sessions and the allowlist. It prints PASS/FAIL per check and exits non-zero on any failure, browser console error or 404. Screenshots go to `tests/output/` (git-ignored). `SHOTS=1` (plus `SHOTS_FONTS=<dir of Roboto .woff2 files>` so the text isn't in the headless browser's fallback font) also saves the phone + desktop gallery in `docs/screenshots/` for the README (tracked; regenerate when the UI changes and add a `shot("name")` call for new features). Look at them for layout work: there's no other way to check layout.

- **Add checks with every feature,** including mocks in the `ctx.route` handler. Pure logic (parsers, validators, Worker routes) goes in `unit.mjs`; anything that needs the page goes in `e2e.mjs`. The e2e blocks run in order and share state (open tabs, settings, mock flags), so a block can depend on the ones before it.
- **Waits:** use `settle(maxMs)` instead of `sleep` after an action: it returns as soon as the page has gone quiet (no requests, socket traffic, DOM changes or short timers pending; tracked by an init script) and never waits longer than `maxMs`. Plain `sleep` is for when another page (PiP, the moved-address page) is involved or you're proving that nothing happens. The app's own long timers have test seams (`window.__timing` → `TEST_TIMING` in app.js: sync delay, color-bump grace, raid tick, clip retry, "Copied!" label, watchdog interval, channel-search debounce; plus `silenceGraceMs`, `joinRetryMs`, `clipPollMs`); add one rather than sleeping through a real timer. Prefer `waitForFunction`/`waitForSelector` when you know what you're waiting for.
- **Browser setup:** set `CHROMIUM_PATH` if the headless shell isn't at the default `~/.cache/ms-playwright/chromium_headless_shell-1234/...` path. If it fails to start over missing shared libraries (libatk, libatk-bridge, libXdamage, libasound, libatspi), `apt-get download` those packages, extract them with `dpkg-deb -x`, and run with `LD_LIBRARY_PATH` pointing at the extracted `usr/lib/x86_64-linux-gnu`. No root needed.
- **Real Twitch is never exercised.** Say so when reporting, and note which behavior is still unverified.
